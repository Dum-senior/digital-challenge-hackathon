# Диспетчер ИИ — Frontend V4.3

Минималистичный интерфейс для кейса «Диспетчерская с возможностями ИИ». Только три сотруднические роли: **диспетчер, инженер, администратор**. Основной стек: **HTML, CSS, vanilla JavaScript**. Без React, npm, CDN и платных фронтенд-сервисов.

> **Демо-режим по умолчанию**. Работающие в браузере сценарии имитируют API на учебных данных из `localStorage`; это **не** подтверждение подключения к PHP, MariaDB, Ollama или голосовому ИИ. Описания предполагаемых API есть в `API_CONTRACT.md`.

## Просмотр

- Откройте готовый самостоятельный файл **`Диспетчер_ИИ_3_роли_V4.html`** — внутри весь CSS/JS; сеть не нужна.
- Или локальный сайт из этого каталога:

```bash
python3 -m http.server 8080
```

Затем откройте `http://localhost:8080`. Вверху справа можно переключить роль в DEMO. В продакшене роли выдаются только сервером.

## Изменения V4.3 — новый раздел администратора «Инженеры»

- Третий пункт в админском меню: **«Инженеры»**.
- Список инженеров с компетенциями, подразделением и текущей нагрузкой.
- На карточке каждого — активные назначенные заявки с номером, описанием, приоритетом и статусом.
- Сводные показатели по инженерам, активным и критическим заявкам; поиск по имени, компетенции и заявке; кнопка «Обновить».
- В DEMO используются учебные записи, а в API-режиме `GET /api/v1/admin/engineers` (контракт в `API_CONTRACT.md`).
- Завершённые заявки не считаются висящими. Если сервер не передаёт компетенции, они не выдумываются.
- Диспетчер и инженер не видят новый раздел. Остальные интерфейсы сохранены.

## Изменения V4.2

В списке инженера добавлены небольшие векторные иллюстрации (встроенные SVG, без внешних библиотек):

- **🕒 Не выполнено** — открытая/новая обычная заявка.
- **🔧 Работа выполняется** — принятая заявка (`in_progress`), значок инструмента плавно движется.
- **🛠 Требует починки** — обычная непринятая заявка, для которой API явно указал `repairRequired: true` (или `repair_required: true`). Это **не дополнительный статус в БД** и не вывод ИИ из одного названия.
- **✅ Выполнено** — `resolved`/`closed`, зелёный значок завершения.

Для показа всех состояний в DEMO добавлены две синтетические заявки #1043 и #1042. Демо хранится отдельно от V4.1. Для критической непринятой заявки **не показываются дополнительные статусы или значки**: только мигающее действие «СРОЧНО ПРИНЯТЬ». После принятия появляется обычное состояние «Работа выполняется». При включённом `prefers-reduced-motion` движение значков отключается.

## Изменения V4.1

**Исправление тревожной строки:** пока критическая заявка не принята, поля «Приоритет» и «Статус» в строке инженера заменяются одним мигающим действием **«СРОЧНО ПРИНЯТЬ»**. Дополнительные метки «Критический» и «Открыта» рядом не показываются. Кнопка «Выполнено» **не отображается** до принятия. После принятия исчезает мигание и возвращаются обычные приоритет/статус.

### Остальное из V4

**Инженер** (раздел «Мои заявки»):
- Красный пульсирующий баннер и **мигающая кнопка «СРОЧНО ПРИНЯТЬ»** в каждой ещё не принятой критической заявке.
- Кнопка «Выполнено» становится доступна после принятия. После «Принять» мигание прекращается; после «Выполнено» закрывается возможность повторного изменения.
- Таймер до срока реакции SLA, если у заявки есть `responseDueAt`/`response_due_at`. Без поля от сервера выводится «SLA не задан» — срок не выдумывается.
- Периодическая проверка новых заявок **раз в 15 секунд** в API-режиме при открытом списке; новая критическая заявка показывает уведомление и мигающий баннер. Это polling, не WebSocket. Для демо есть кнопка «Создать новую тревогу» (только DEMO).
- Назначенные заявки, без колонки «Исполнитель». Карточка сохраняет предложенное решение и источники. Рабочие статусы: `new/open → in_progress → resolved`.

**Диспетчер:**
- Прежние страницы и кнопки, анализ, исправление описания и ручное подтверждение.
- Раскрываемый блок **извлечённых сущностей**: оборудование, объект, этаж, кабинет, IP, серийный номер, симптомы и теги. Пустые поля не заменяются домыслами.
- Уверенность классификации показывается, **только если API вернул значение**; иначе «Не указана». Подтверждение человеком обязательно.
- Выбор скриншота (PNG/JPG/WebP, до 5 МБ). В API-режиме после создания заявки предусмотрен POST загрузки; в DEMO прямо сказано, что файл не сохранён. Согласуйте endpoint с разработчиком API.

**Администратор:**
- Статистика по приоритетам и статусам отображается как лёгкие горизонтальные диаграммы **без внешних библиотек**.
- Блок SLA показывает реальные серверные агрегаты `sla.atRisk` и `sla.breached` только при наличии данных.
- Журнал действий загружается кнопкой на странице статистики через API.
- Отдельная раскрываемая панель замера фактического **времени и количества действий** для двух вариантов обработки — вручную и с ИИ. Измерения не выдумывают эффективность и не пишутся в БД.
- Управление базой знаний (создать, редактировать, удалить, добавить URL сайта) сохранено из V3. Добавление сайта в DEMO только сохраняет ссылку, не скачивает контент.

## Безопасность и доступность

- «СРОЧНО ПРИНЯТЬ» мигает **красным текстом и кнопкой**, без звуковых сигналов. Для пользователей с `prefers-reduced-motion: reduce` анимация отключается, но красная тревога остаётся видна.
- Данные заявок выводятся с HTML-экранированием; основную проверку прав, SLA и переходов статусов должен обеспечивать сервер.
- Frontend не получает пароли MariaDB или ключи Ollama.
- Для работы браузерного микрофона вне `localhost` нужен HTTPS.

## Подключение к проекту

Поместите весь каталог в отдельную frontend-ветку, не заменяя корневые PHP-файлы репозитория. Согласуйте endpoints `API_CONTRACT.md`; адаптируйте `js/api.js`, затем выставьте в `js/config.js`:

```js
window.DISPATCH_CONFIG = { mode: 'api', apiBase: '/api/v1', csrfToken: null, currentUser: null };
```

В `api`-режиме `currentUser` и CSRF должны приходить из защищённой сессии PHP, а не из браузерного переключателя ролей. Не публикуйте фронтенд напрямую поверх старой UI-системы до интеграционных тестов.

## Что реально проверено

- `node --check` для `js/app.js`, `js/api.js`.
- Рендер трёх ролей в Chromium (через вставку автономного HTML в изолированную страницу).
- Воспроизведение тревоги, принятие и завершение критической заявки, исчезновение мигающей кнопки, создание новой демо-тревоги.
- Форма извлечённых полей диспетчера, статистика и журнал админа, работа секундомера.
- Снимки интерфейса для desktop и mobile. JavaScript-ошибок в этих проверках нет.

**Не проверено:** серверные PHP endpoints, авторизация, звонки, настоящая Qwen/RAG, MariaDB и реальная доставка уведомлений. Эти части требуют интеграции с backend и повторных E2E тестов в настоящем окружении.
