# Диспетчер ИИ

Диспетчер преобразует текст, аудио или скриншот в черновик, проверяет категорию, место, приоритет и исполнителя. Инженер принимает заявку, получает рекомендации с источниками и отмечает выполнение. Администратор видит статистику, SLA, журнал, базу знаний и список инженеров с тегами компетенций.

## Стек и требования

- HTML, CSS и JavaScript. Фронт основан на ветке `Димас`.
- PHP 8.3, Apache и MariaDB 11.4. База хранит сотрудников, компетенции, заявки, черновики, SLA и журнал.
- Python 3.12, FastAPI, Tesseract (русский и английский). Whisper large-v3-turbo расшифровывает голос, Qwen2.5 1.5B разбирает текст и формулирует рекомендации, BGE-M3 ищет по 78 инструкциям. Веса остаются на хосте, контейнер вызывает модели по внутренней сети.
- Для приложения с уже запущенными моделями ориентир для демо — Linux x86-64, 2 vCPU, 4 ГБ RAM и 15 ГБ свободного места. Для приложения и моделей на одном хосте ориентир — 8 vCPU, 16 ГБ RAM, 30 ГБ свободного места, NVIDIA с 8 ГБ VRAM для GPU-сборки Whisper. Полный стек рассчитан на один демонстрационный поток. Эти значения — оценки ёмкости, гарантированный минимум не измерялся.
- Нужны Docker Engine с Compose v2, HTTPS для микрофона вне localhost и доступ к реестрам образов при сборке.

## Деплой в /srv/release

1. Скопируйте исходники в `/srv/release`. Сделайте `cp .env.release.example .env` и `chmod 600 .env`. Задайте значения `DB_PASS` и `DISPATCHER_API_TOKEN` (например, сгенерируйте через `openssl rand -hex 32`), три отдельных пароля от 12 символов, `APP_URL` и `WEB_PORT`.
2. На хосте должны отвечать Whisper на `127.0.0.1:8090/inference`, llama.cpp с Qwen2.5 1.5B на `127.0.0.1:11436` и llama.cpp с BGE-M3 на `127.0.0.1:11437`. Для стандартного Linux-моста Docker `172.17.0.1` установите пакет `socat`, скопируйте `docker/dispatcher-model-bridge@.service` в `/etc/systemd/system/`, выполните `systemctl daemon-reload` и `systemctl enable --now dispatcher-model-bridge@8090 dispatcher-model-bridge@11436 dispatcher-model-bridge@11437`. Для другого адреса укажите доступный контейнерам `MODEL_HOST` и настройте мост под него.
3. Выполните `docker compose up -d --build`. MariaDB сначала становится healthy, затем отдельный контейнер применяет миграции и наполняет пустую БД демо-справочниками. Веб-сервис и ИИ-API запускаются после успешного завершения инициализации. API строит индекс по Markdown при запуске.
4. Настройте HTTPS-реверс-прокси на `127.0.0.1:WEB_PORT`. Передавайте `Host`, `X-Forwarded-Proto` и `X-Forwarded-For`, разрешите тело до 21 МиБ и таймаут чтения 120 секунд. MariaDB и ИИ-API доступны внутри Compose.
5. Проверьте `docker compose ps -a`, `docker compose logs migrate inference` и вход на `/login`. Логины `dispatcher@demo.test`, `engineer@demo.test`, `admin@demo.test`. Пароли заданы в `.env`.

Данные MariaDB и вложения хранятся в постоянных томах. Для обновления сделайте резервную копию БД и повторите `docker compose up -d --build`. Добавляйте инструкции в `services/dispatcher-api/kb/`; сборка и перезапуск inference перестраивают индекс. Демо-адреса объектов синтетические.

## Проверки

`sh docker/test-release.sh` запускает отдельный Compose-проект с чистой MariaDB, случайными тестовыми паролями и отдельными томами. Тест проверяет права, аварию, правки и подтверждение черновика, назначение, принятие и завершение инженером, отчёт и журнал. Требуется доступ к локальным моделям. Для параллельного запуска задайте `TEST_PORT`.

## Демонстрация без входа

Установите `DISPATCHER_DEMO_ROLES=true` в `.env` и пересоздайте web: `docker compose up -d web`. Главная и `/login` сразу открывают рабочее пространство. Вверху справа выбирается Диспетчер, Инженер или Администратор. Используются только существующие аккаунты `*@demo.test` из release-seed; новые пользователи не создаются. Это открытый демонстрационный доступ к этим ролям, не производственная авторизация. При `false` сохраняется обычный вход.
