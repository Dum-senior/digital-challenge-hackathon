# Исследование открытых компонентов и план закрытого развёртывания

Дата проверки первичных источников: 14.11.2026. Область: модуль Дена, текст → структурированный черновик. Документ описывает варианты и будущую инфраструктуру; купленный сервер, установленная модель и фактически работающий внешний endpoint пока не подтверждены. Приведённые оценки памяти — планирование, не результаты нагрузочного теста.

## 1. Граница ответственности

Модуль получает текст из формы, исправленный транскрипт Вани или текст телефонного источника Кирюхи; возвращает факты, вопросы, категорию, критичность и рекомендацию исполнителя. Интегратор сохраняет черновик в OpenHelpDesk, проверяет права пользователя и проводит подтверждение. Здесь не нужны новый STT, новая база пользователей, телефония, RAG и интерфейс инженера.

Справочник инженеров и доступная нагрузка должны приходить из доверенного интеграционного слоя. Модель не выбирает произвольный ID: результат проверяется по фактическим данным. При отсутствии живого справочника демонстрационные записи маркируются как synthetic; это не доказательство интеграции с upstream.

## 2. Три варианта inference

| Вариант | Когда выбирать | Проверенные возможности | Ограничения |
| --- | --- | --- | --- |
| vLLM + Qwen2.5-7B-Instruct | Первый серверный кандидат для текста | OpenAI-compatible API, ограничение генерации JSON Schema | Проверить конкретную версию, GPU и нагрузку; native Windows не является поддерживаемой платформой |
| Ollama local + Qwen2.5 | Быстрая разработка на Windows/ноутбуке | JSON Schema через format, локальный inference | Локальный bind не заменяет авторизацию шлюза; отключить cloud-функции |
| llama.cpp + GGUF | Ограниченная память, CPU/GPU или резервный запуск | Квантизованные модели, HTTP API, schema-constrained JSON | Выбрать совместимый GGUF и измерить скорость; лицензия конкретного артефакта проверяется отдельно |

[vLLM structured outputs](https://docs.vllm.ai/en/latest/features/structured_outputs/) показывает передачу Pydantic JSON Schema в response_format. Повторная серверная валидация обязательна: корректный JSON не гарантирует истинность значений.

[Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs) поддерживает схему в format, включая vision-модели. В [Ollama FAQ](https://docs.ollama.com/faq) описан local-only режим OLLAMA_NO_CLOUD=1; текущая документация отличает его от cloud-моделей.

[llama.cpp](https://github.com/ggml-org/llama.cpp) и [описание HTTP-сервера](https://raw.githubusercontent.com/ggml-org/llama.cpp/master/tools/server/README.md) подтверждают CPU/GPU inference, OpenAI-compatible маршруты и ограничение JSON схемой.

## 3. Модели для сравнительного теста

1. **Qwen2.5-7B-Instruct — базовый кандидат.** Model card явно перечисляет русский язык, работу со структурированными данными и JSON. 7.61B параметров. Для intake достаточно начать с ограниченного контекста 4096–8192 токенов, а не максимального окна. [Model card](https://huggingface.co/Qwen/Qwen2.5-7B-Instruct).
2. **Qwen3-8B — альтернативный кандидат.** Проверить качество на тех же русских обращениях, формат reasoning/content и работу schema-constrained режима. Более новая модель не считается лучшей до измерения. [Model card](https://huggingface.co/Qwen/Qwen3-8B).
3. **Qwen2.5-VL-7B-Instruct — кандидат для отдельной следующей стадии фото/скриншотов.** Поддерживает изображение + текст; качество русских кодов ошибок, мелкого текста и нечитаемых символов нужно измерить. В задаче Дена P0 — текстовый контракт; не внедрять второй независимый поток заявок. [Model card](https://huggingface.co/Qwen/Qwen2.5-VL-7B-Instruct).

Все три указанные model cards на дату проверки объявляют Apache-2.0. Для весов фиксировать полное имя, revision/hash и источник; для производных quantization-артефактов проверить отдельную карточку. Не использовать trust_remote_code без необходимости и ревью.

## 5. Закрытый контур и токены

В этом плане «закрытая модель» означает открытые веса на собственном сервере с контролируемым сетевым доступом. Это не proprietary модель с недоступными весами. После предварительного скачивания весов, контейнеров и зависимостей inference можно изолировать от внешнего интернета; фактическую автономность подтвердить отдельным тестом с отключённым egress.

План потока:

```text
OpenHelpDesk backend
  -> dispatcher_ai (Authorization: Bearer DISPATCHER_API_TOKEN)
  -> внутренний inference endpoint (LLM_API_KEY)
  -> JSON, валидация, рекомендация
  -> OpenHelpDesk: сохранение и ручное подтверждение
```

- **DISPATCHER_API_TOKEN** — секрет входа в модуль Дена. Генерируется локально криптографически стойким генератором; хранится только в окружении/secret store сервера и интегратора. Сам по себе сгенерированный токен не создаёт удалённый сервис.
- **LLM_API_KEY** — отдельный секрет dispatcher → inference gateway. Это не пользовательский session token и не Hugging Face token скачивания весов.
- Для vLLM значение upstream-ключа настраивается через VLLM_API_KEY или API-key настройку запуска. Не передавать секрет в вывод shell, чат, git remote, журналы или URL.
- API key vLLM защищает только перечисленные API prefixes, а не весь HTTP сервер. Поэтому сетевой доступ и служебные endpoints ограничиваются отдельным gateway/firewall. См. [vLLM security](https://docs.vllm.ai/en/latest/usage/security/).
- Браузер не обращается напрямую к inference и не получает оба ключа. TLS и ограничения на размер, частоту, параллелизм, таймаут применяются на входе.
- Не логировать исходный текст целиком по умолчанию. Для качества сохранять согласованные синтетические примеры; для эксплуатации определить политику хранения с командой безопасности.
- Отключить облачные fallback-маршруты: при отказе своей модели вернуть failed/manual-review, а не незаметно отправить заявку стороннему провайдеру.

В этом документе нет настоящих токенов. Сервер ещё не развёрнут, модель не загружена и рабочий endpoint не проверен.

## 6. uv и воспроизводимость

Python-зависимости приложения вести через pyproject.toml и uv.lock. Рабочая схема: uv sync --frozen, затем uv run для запуска команд проекта. Lock-файл фиксирует Python-пакеты, но не заменяет фиксацию Docker digest, версии CUDA/драйвера, model revision и inference engine. [Официальный workflow uv](https://docs.astral.sh/uv/guides/projects/).

На дату проверки [vLLM GPU installation](https://docs.vllm.ai/en/latest/getting_started/installation/gpu/) указывает Linux, Python 3.11–3.14, NVIDIA compute capability не ниже 7.5; Windows нативно не поддерживается. Официальная страница рекомендует uv. Конкретный совместимый набор версий выбирается после получения сервера. Не переносить автоматически случайную свежую версию PyTorch/CUDA в проверенное окружение.

## 7. Планирование сервера

Расчёт нижней границы весов для 7.61B: BF16/FP16 ≈ 7.61 млрд × 2 байта ≈ 15.2 GB (десятичные) только весов. Теоретический 4-bit payload ≈ 3.8 GB; реальные quantized файлы добавляют метаданные/групповые коэффициенты. Runtime, KV-cache, batching, vision encoder и буферы увеличивают память.

**Предварительный ориентир, не минимальное требование и не обещание производительности:** одна GPU класса 24 GB, 64 GB RAM, NVMe с запасом под несколько весов/контейнеров. При параллельной загрузке STT, vision, dispatcher и engineer-моделей этого может не хватить. Рассмотреть общий текстовый inference вместо нескольких одинаковых копий, отдельную очередь запросов и выгрузку редко используемых моделей.

Перед покупкой окончательной конфигурации арендовать сопоставимый GPU или выполнить короткий прогон: 1/2/4 одновременных запроса, контекст 4K/8K, реальные размеры ответа. Измерять memory peak, p50/p95 latency, requests/min, долю valid JSON, качество полей и аварийных случаев. Не выводить скорость из числа параметров и не обещать токены/с без замера. Согласовать бюджет, допустимую задержку и требования к отказоустойчивости.

## 9. Матрица проверки качества

Базовые десять русских обращений из ТЗ расширить контрастными парами: «принтер дымит» / «дыма нет»; «нет счётчика» / «нет показаний счётчика»; «нет доступа у одного» / «заблокирована работа нескольких отделов». Добавить опечатки и особенности транскрипции, противоречивое уточнение, неизвестный объект, некорректный IP, prompt injection и просьбу назначить несуществующего инженера.

Для каждой записи проверять category, приоритет по явно описанной демополитике, поля и null, missing_fields, вопросы, recommendation ID из справочника. Не оценивать точность только по совпадению категории. Отдельные инварианты: нет автоматического назначения, не придуманы IP/серийник, неизвестное не заменяется фактом, время ожидания не делает инцидент аварией.

Измерять отдельно тесты приложения (включая подставной ответ HTTP), live-evaluation настоящей модели и нагрузку. Успешные unit-тесты не являются измерением точности ИИ. Сохранять размер выборки, revision модели, параметры генерации, дату, ошибки и задержки. При невалидном JSON, таймауте или отсутствующем upstream возвращать понятный failed и ручной путь без фиктивной рекомендации.

## 10. Порядок внедрения

1. Зафиксировать контракт Дена с интегратором и справочник реальных категорий/ID, не менять общие маршруты молча.
2. Проверить модуль локально через uv на синтетике и подставном upstream, включая ошибки.
3. На выделенном сервере установить один inference engine, скачать и зафиксировать одну текстовую модель.
4. Настроить сетевые границы, два отдельных токена, секреты, ограничение нагрузки и отсутствие внешнего fallback.
5. Прогнать live-evaluation и краткий load test; записать фактические результаты. Скорректировать модель/квантизацию/контекст по данным.
6. Подключить OpenHelpDesk к модулю, провести сквозную проверку с Ваней и интегратором, затем отправить отдельный PR. Не менять STT, телефонию, RAG или права пользователей в этой ветке.

Фото/vision, оптимизация GPU sharing, фоновые SLA-уведомления и рабочие регламенты — следующие согласованные изменения. Этот документ не подтверждает их реализацию.
