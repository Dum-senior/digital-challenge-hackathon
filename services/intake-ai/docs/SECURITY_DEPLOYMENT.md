# Безопасное self-hosted развёртывание

## Сервер и сеть

Пробный вариант: Linux, x86_64, 64 GB RAM, NVMe 1 TB, GPU с **от ~24 GB VRAM** для 8B BF16-инференса с запасом на KV cache/контекст. Это оценочный профиль, а не гарантия скорости/вместимости: измерить фактическую VRAM, batch, токены/сек и p95 latency на купленном железе. Для CPU/меньшего VRAM рассмотрите квантованный GGUF и `llama.cpp`, затем замерьте качество на русскоязычных тестах. Отдельно учесть STT Вани и RAG Дмитрия, их память и одновременность запросов.

Связь:

```text
OpenHelpDesk PHP/MySQL -> [127.0.0.1:8091 intake-ai] -> [127.0.0.1:8000 vLLM]
                                                  \-> Qwen3-8B weights ON SERVER
```

Оба порта изолированы от интернета; SSH только через VPN, TLS для внешнего frontend, firewall default deny; модельные эндпоинты не публикуем. Обновления пакетов/весов — вручную в разрешённом окне, с проверкой хеша/лицензии и тестом rollback. Услуги из чужого облака по умолчанию запрещены.

## Пример запуска после provisioning

```bash
# На целевом сервере, под сервисным пользователем: два РАЗНЫХ случайных ключа.
python -c 'import secrets; print(secrets.token_urlsafe(48))'
# Сохраните первый в INTAKE_SERVICE_TOKEN, второй в LLM_API_KEY
# Например, в /etc/dispatcher-ai/intake.env с правами 0600, владельцем service-account.

# Запустите модель через официальный vLLM Docker image или управляемый uv environment;
# vLLM прочитает VLLM_API_KEY из окружения (то же значение, что LLM_API_KEY клиента).
# Конкретный runtime, CUDA, версия модели и образ выбираются после проверки GPU.
# Не прокидывайте порт vLLM во внешний сетевой интерфейс.

cd services/intake-ai
uv sync --no-dev
# Среда для service account; НЕ храните токены в команде, истории shell или git.
uv run uvicorn intake_ai.service:app --host 127.0.0.1 --port 8091 --workers 1
```

Для production обязателен systemd или контейнерный supervisor с `Restart=on-failure`, ограничениями памяти и процессора, readiness-проверкой LLM отдельно от `/healthz`. Отключить debug traceback/сырые тексты в логах. Добавить метрики только по длительности/статусам без содержимого заявок, секретов и персональных данных.

## Секреты и API токены

`INTAKE_SERVICE_TOKEN`: серверный токен PHP -> intake-ai (проверяется по constant-time compare). `LLM_API_KEY`: отдельный токен intake-ai -> vLLM, передаётся как `Authorization: Bearer` и сверяется модельным сервером. `VLLM_API_KEY` на сервере инференса = значение `LLM_API_KEY` у клиента. Готового коммерческого ключа нет и он не требуется при on-prem работе. Ни одно значение не записывается в пример `.env`, git, отчёт тестов или frontend.

vLLM документация предупреждает: `--api-key` НЕ защищает некоторые другие маршруты (например `/invocations`), поэтому **loopback + firewall + reverse proxy с allowlist** обязательны, даже с токеном. Сетевой слой — отдельная защита, не заменяемая JWT.

Не доступен on-prem сервер => `ENABLE_LLM=false` и честная пометка `rules_only`. Сеть оборвалась/модель упала => `failed` + ручная обработка, без автоматических назначений. Запрещено выдавать внешнюю модель за закрытую или передавать производственные данные в сторонний сервис без письменного разрешения.

## Политики

- Авторизация пользователей и подтверждение только в PHP; доступы проверяются заново перед сохранением и перед подтверждением.
- Входные тексты недоверенные, модель никогда не вызывает инструменты, не исполняет команды и не управляет промышленным оборудованием.
- Сервис обрабатывает только минимум полей. Нет самостоятельной базы и журналов сырых текстов; хранение/срок удаления организует команда в OpenHelpDesk.
- Нет автоматического экспорта телефонных разговоров; STT/телефония другого участника.
- Сроки/категории SLA нужно согласовать с владельцем регламента. Риск по 30-минутному окну — учебное правило.
- Сравнить SLA, полномочия и `api_rate_limits` PHP-приложения при объединении, не открывать сервис в публичный интернет.
