# Диспетчер ИИ V4.3 — контракт для разработчика API

**Только три роли:** `dispatcher`, `engineer`, `admin`. **Все маршруты в этом файле являются ожидаемым frontend-контрактом, а не гарантированно существующими endpoint'ами**. Сверьте с текущими PHP-роутами и адаптируйте `js/api.js` без переписывания экрана.

## Главное правило

Все ИИ, RAG, телефония, STT, MariaDB, аутентификация и обработка ссылок — **на сервере**. Frontend не получает сервисных секретов, не обращается напрямую к Ollama и не определяет опасность самостоятельно в API-режиме. Демо-режим использует локальные примеры только для показа интерфейса.

| Кто | Операция | Метод и ожидаемый путь | Данные / результат |
|---|---|---|---|
| Диспетчер | Список заявок | `GET /api/v1/tickets` | Массив или `{tickets:[...]}` |
| Диспетчер | Заявка | `GET /api/v1/tickets/{id}` | `{id,subject,description,priority,status,assigneeId,assigneeName,location}` |
| Диспетчер | Анализ | `POST /api/v1/intake/analyze` | `{text,source}` → черновик |
| Диспетчер | Уточнить | `POST /api/v1/intake/drafts/{id}/clarify` | `{text}` → обновлённый черновик |
| Диспетчер | Подтвердить | `POST /api/v1/intake/drafts/{id}/confirm` | Откорректированные поля → `{ticket_id}` |
| Диспетчер | Распознать аудио | `POST /api/v1/intake/transcriptions` | `multipart/form-data`, `audio`, `source=browser` → `{text}` |
| Диспетчер | Исправить текст заявки | `POST /api/v1/tickets/{id}/update` | `{subject,description}` → обновлённая заявка |
| Диспетчер | Очередь входящих | `GET /api/v1/intake/submissions` | Массив новых обращений, если используется |
| Диспетчер | Инженеры | `GET /api/v1/admin/users` **(временно)** | Нужен безопасный список исполнителей; лучше отдельный `/meta/assignees` с правом диспетчера |
| Диспетчер | Категории | `GET /api/v1/meta` | Список категорий |
| Инженер | Мои заявки | `GET /api/v1/tickets` | Сервер фильтрует по текущему инженеру/правам |
| Инженер | Предложенное решение | `POST /api/v1/tickets/{id}/engineer-assist` | `{status,summary,steps,sources}` |
| Инженер | Принять заявку в списке | `POST /api/v1/tickets/{id}/update` | `{status:"in_progress"}` |
| Инженер | Отметить выполненной в списке | `POST /api/v1/tickets/{id}/update` | `{status:"resolved"}` |
| Админ | Статистика из БД | `GET /api/v1/admin/reports/tickets?from=YYYY-MM-DD&to=YYYY-MM-DD` | Сводка ниже |
| Админ | Список статей | `GET /api/v1/kb/articles` | Массив статей |
| Админ | Просмотр статьи | `GET /api/v1/kb/articles/{id}` | Статья |
| Админ | Создать статью | `POST /api/v1/admin/kb/articles` | `{title,description,category,content:[...]}` |
| Админ | Редактировать статью | `PATCH /api/v1/admin/kb/articles/{id}` | Поля статьи |
| Админ | Удалить статью | `DELETE /api/v1/admin/kb/articles/{id}` | `{deleted:true}` |
| Админ | Импорт URL сайта | `POST /api/v1/admin/kb/import-website` | `{url}` → ссылка/статус индексации |

**Важно:** маршрут `/admin/users` для диспетчера может возвращать HTTP 403, если RBAC корректно ограничивает доступ. API-разработчику нужно дать диспетчеру отдельный **read-only список исполнителей**, не раскрывая чужие административные данные. До этого диспетчерская форма назначения не будет полностью подключена в API-режиме.

## Примеры JSON

Черновик для подтверждения:

```json
{
  "draft_id": "d-0123",
  "extracted": {"subject":"Принтер дымится", "description":"Принтер не печатает, из него идёт дым", "category":"Безопасность", "location_name":"Кабинет 205"},
  "recommendation": {"priority":"critical", "assignee_id":null, "reason":"Признаки опасности"},
  "questions": [],
  "requires_human_review": true
}
```

Ожидаемый ответ `engineer-assist`:

```json
{
  "ticket_id": 1048,
  "status": "answered",
  "summary": "Рекомендуемые безопасные действия",
  "steps": ["Прекратить использование неисправного устройства", "Сообщить ответственному специалисту"],
  "sources": [{"type":"kb", "id":3, "title":"Дым или запах гари от офисного оборудования"}]
}
```

Если источники есть, а генерации нет: `status:"sources_only"`, `sources:[...]`, `steps:[]`. Если ничего нет: `status:"no_sources"`. Не возвращать выдуманных источников.

Ожидаемый ответ статистики:

```json
{
  "from":"2026-11-01", "to":"2026-11-30", "total":25, "open":9, "resolved":16, "critical":3,
  "byPriority":{"low":8,"medium":9,"high":5,"critical":3},
  "byStatus":{"new":2,"open":4,"in_progress":3,"resolved":12,"closed":4}
}
```

## Матрица полномочий (обязательно на сервере)

- **Dispatcher:** ввод, анализ и подтверждение заявок; исправление `subject/description`. Не должен иметь доступ к управлению базой знаний или административной статистике.
- **Engineer:** в списке каждой назначенной заявки есть кнопки «Принять» и «Выполнено», колонки «Исполнитель» нет. `GET` только назначенных ему заявок, доступ к рекомендациям по разрешённым заявкам; разрешены только переходы `new/open → in_progress → resolved` с фиксацией пользователя и времени. Не может редактировать приоритет, чужие заявки, статьи или системные настройки.
- **Admin:** запрос агрегированной статистики MariaDB и CRUD базы знаний. Не должен автоматически видеть сервисные секреты или управлять Ollama из браузера.

Пользовательский выбор роли в DEMO не предоставляет права. Используйте сессию на сервере, same-origin cookies / CSRF, ограничение частоты и аудит изменений. Проверьте возможность редактирования текста заявки после создания: сервер должен записывать историю изменений, особенно если заявка уже принята инженером.

## Импорт сайта: безопасность и автономность

`POST /admin/kb/import-website` должен проверять допустимость URL и переадресаций, блокировать loopback, link-local, приватные и служебные адреса, учитывать защиту от SSRF, ограничивать размер/время скачивания, HTML и количество страниц. Индексация может быть асинхронной, тогда возвращайте ID задачи и статус. Не выполняйте прямые запросы к произвольным адресам из браузера с сервисными правами.

Если проект разворачивается в закрытой локальной сети, сайт из публичного интернета **не скачается**. Предусмотрите заранее импортированные инструкции или разрешённый внутренний источник.

## Технические примечания

- Используйте локальные ресурсы — CSS, JS без внешних CDN.
- Для браузерного микрофона нужен HTTPS либо `localhost`.
- Защищённые endpoints должны проверять роли, ресурсную принадлежность, допустимые статусы, размеры входа и CSRF.
- Экраны на фронтенде готовы в `demo`; real API не подтверждён до интеграции.

## Дополнение V4: новые поля и операции

Для первой совместной интеграции сохраняйте существующие пути из таблицы выше. В V4 появились следующие дополнительные требования:

| Экран / действие | Контракт | Важные условия |
|---|---|---|
| Инженер: **SLA** | В `GET /api/v1/tickets` желательно передавать `responseDueAt` или `response_due_at` в ISO 8601 (со смещением часового пояса) | Срок вычисляет backend по регламенту; клиент только показывает обратный отсчёт. Когда поля нет, показываем «SLA не задан» |
| Инженер: **обновления** | Повторный `GET /api/v1/tickets` каждые 15 секунд на странице инженера | Сервер фильтрует только назначенные текущему пользователю; запретить чтение чужих заявок |
| Инженер: **статусы** | `POST /api/v1/tickets/{id}/update` с `{ "status": "in_progress" }` или `{ "status": "resolved" }` | Только назначенный инженер и только допустимый переход; зафиксировать время принятия/закрытия, защититься от гонок |
| Диспетчер: **оценка уверенности** | `POST /api/v1/intake/analyze`: `recommendation.confidence` или `confidence` (необязательное число 0–1) | Не рассчитывать процент самостоятельно; для низкой уверенности выдавать уточняющие вопросы, ручное подтверждение обязательно |
| Диспетчер: **извлечённые поля** | `extracted.equipment`, `object`, `floor`, `room`, `ip`, `serial_number`, `symptoms`, `tags`, `location_name` | Пустые поля не придумывать; при `confirm` frontend передаёт необязательный объект `extracted` с исправлениями диспетчера |
| Диспетчер: **скриншот** | `POST /api/v1/tickets/{id}/attachments`, `multipart/form-data` с полем `image` | Endpoint **предлагаемый, не подтверждён**. Ввод PNG/JPEG/WebP, ≤5 МБ, MIME/содержимое проверяет сервер, файл хранится вне webroot |
| Админ: **журнал** | `GET /api/v1/admin/audit` | Формат: `[{when,actor,action,target}]` либо `{events:[...]}`; только администратор |
| Админ: **статистика SLA** | Дополнительное поле в `GET /api/v1/admin/reports/tickets` | `sla: {atRisk: number, breached: number}`. При отсутствии этого поля не выводить выдуманные значения |
| Админ: **замер эффективности** | API не требуется | Секундомер и ввод количества действий работают в браузере, измерения не претендуют на БД-аналитику |

### Пример дополненного ответа `/intake/analyze`

```json
{
  "draft_id": "d-0123",
  "extracted": {
    "subject": "Принтер не печатает и дымится",
    "description": "Кабинет 205, из принтера идёт дым",
    "equipment": "Принтер",
    "object": "Офис",
    "floor": "2",
    "room": "205",
    "ip": null,
    "serial_number": null,
    "symptoms": ["не печатает", "идёт дым"],
    "tags": ["оргтехника", "безопасность"]
  },
  "recommendation": {
    "priority": "critical",
    "confidence": 0.93,
    "assignee_id": 2,
    "reason": "Потенциальная угроза безопасности"
  },
  "questions": [],
  "requires_human_review": true
}
```

Это **пример формата для согласования**, а не утверждение, что модель уже возвращает именно эти данные. Не создавайте фиктивную уверенность на сервере: либо передайте реально обоснованную оценку, либо `null`.

### Остальные важные ограничения

- Важность сообщения «100 принтеров не работает» должен определять backend Дена по признакам масштаба. Слово «сеть» — только гипотеза, пока нет проверки.
- Критический случай «принтер дымится» требует аварийной эскалации и принудительной защиты правилом, а не только LLM.
- Результат RAG предоставляет backend; интерфейс инженера не должен инициировать опасные действия с устройствами.
- API-режим не использует искусственные демо-классификации. Для реальной телефонии и уведомлений требуются отдельные серверные интеграции.


## V4.2 — Визуальное состояние инженера (не меняет workflow)

Список инженера отображает состояния по уже существующему полю `status`:

| `status` | Значок и подпись |
|---|---|
| `new`, `open` | Часы — «Не выполнено» |
| `in_progress` | Инструмент — «Работа выполняется» |
| `resolved`, `closed` | Галочка — «Выполнено» |

**Необязательное поле** `repairRequired: true` (или `repair_required: true`) при `status=new/open` заменяет нейтральную подпись на «Требует починки» с иконкой инструмента. Не нужно добавлять новый статус `needs_repair` в PHP или MariaDB: это только признак типа неисправности. Если флага нет, фронт ничего не предполагает.

Для `priority=critical` и `status=new/open` **в строке только «СРОЧНО ПРИНЯТЬ»**, независимо от `repairRequired`. Значки приоритета и статуса скрыты до принятия, и кнопка «Выполнено» полностью скрыта. После принятия появляются обычные статусы и кнопка завершения. Существующие API-запросы не меняются.


## V4.3 — «Инженеры» в рабочем пространстве администратора

**Новый обязательный read-only endpoint для интеграции с MariaDB:**

`GET /api/v1/admin/engineers` — доступен **только администратору**.

Ответ содержит только пользователей с ролью `engineer`, их реально сохранённые компетенции и закреплённые заявки. Поля `tickets` включают активные заявки (`new`, `open`, `in_progress`, при наличии `needs_clarification`). Завершённые `resolved`/`closed` можно не передавать; при желании API может присылать их, но интерфейс отображает только активные. Сервер обязан проверить RBAC, а данные выбирать из MariaDB.

```json
{
  "engineers": [
    {
      "id": 2,
      "name": "Мария Иванова",
      "department": "Поддержка рабочих мест",
      "competencies": ["Оргтехника", "Принтеры и МФУ", "Рабочие станции"],
      "tickets": [
        {"id": 1048, "subject": "Принтер дымится", "priority": "critical", "status": "open", "location": "Кабинет 205"},
        {"id": 1046, "subject": "Закончился тонер", "priority": "low", "status": "in_progress", "location": "Кабинет 214"}
      ]
    }
  ]
}
```

Здесь значения **учебные для согласования схемы**, не данные реальной БД. Клиент также понимает `skills` вместо `competencies` и `active_tickets`/`assigned_tickets` вместо `tickets`.

### Условия безопасности и корректности

- Не передавать пароль, хэш пароля, телефон, персональные токены, секреты или закрытые пользовательские поля.
- В `competencies` передавать **фактически сохранённые** в БД данные. Если компетенции нигде не хранятся, отдавать `[]`, а не выдумывать значения из категории заявки.
- Использовать реальные связи `ticket.assignee_id → users.id` (названия колонок могут отличаться — сверить схему). Нельзя определять исполнителя по тексту заявки.
- Считать нагрузку по активным назначенным заявкам. Завершённые заявки не считать висящими.
- API возвращает список, а не только количество. Когда `active_count` положительный, но `tickets` отсутствует, фронт показывает предупреждение.
- Защитить endpoint авторизацией, проверкой роли, фильтрацией чувствительных полей и разумными лимитами размера ответа.
- Диспетчер и инженер не должны иметь доступ к этому административному endpoint.
- При ошибке авторизации/сети интерфейс сообщает о проблеме и **не отображает демо-сотрудников** в режиме API.
- Фронтенд в режиме `demo` читает синтетические данные из `localStorage`, а не из MariaDB.

### Сценарии для проверки

1. Админ открывает «Инженеры» и видит инженеров, компетенции и активные заявки.
2. Принятая заявка переходит в «В работе», статистика нагрузки обновляется после «Обновить».
3. Завершённая заявка исчезает из активного списка после обновления.
4. Поиск находит инженера по имени, компетенции и номеру заявки.
5. У инженера без компетенций отображается «Компетенции не указаны в БД».
6. Для неадминистратора endpoint возвращает 403, а маршруты админки скрыты.
