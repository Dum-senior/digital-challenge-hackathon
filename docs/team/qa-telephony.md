# Безопасность, QA и телефония

- [Запуск тестового стенда](../../README_TESTING.md).
- [Результаты проверок и ограничения](../../TEST_RESULTS.md).

В REST API доступ к вложению требует доступа к заявке. Для вложения внутренней
заметки нужны права сотрудника. Это правило действует и при скачивании, и при
добавлении файла в заметку. Ответ со скачиванием имеет `Cache-Control: private,
no-store`. HTTP-тесты используют синтетические файлы вне `public/`.

История, список и мобильная сводка используют ту же проверку конфиденциальности,
что и карточка. Конфиденциальные заявки без группы не выдаются через эти
REST-маршруты. REST API проверяет статус и справочные ID до записи изменений.
Невалидный JSON и неверные типы проверенных полей получают контролируемый отказ.
Пакет вложений проверяется целиком до сохранения, а при ошибке записи метаданных
строки откатываются и файлы удаляются. Неверный тип CSRF-токена отклоняется.
Форма входа и callback Microsoft SSO проверяют типы полей. Отладочный журнал
SSO сохраняет этапы и коды ошибок без профилей пользователей, данных запроса
OAuth и тел ответов провайдера.

При следующей интеграции приоритетны права на черновики и подтверждение,
идемпотентность, настройки отправки данных внешней модели и аудит маршрутов
голоса. Существующий помощник инженера блокирует конфиденциальные заявки;
автотест подтверждает, что их содержимое не доходит до провайдера.

Для интеграции сначала проверить согласованный формат аудио на обычном голосовом
входе. Телефонный вход передаёт запись в тот же STT, а транскрипцию — в тот же
анализ с `source=phone`. Диспетчер получает черновик для подтверждения. Для
вебхука понадобятся проверка подписи и времени события, идемпотентность по ID
звонка, ограничения файла, приватное хранение и удаление по сроку. Реальная АТС
не подключена.
